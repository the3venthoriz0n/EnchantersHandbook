# Enchanter's Handbook

Quality-of-life tools for enchanters in Skyrim Special Edition / Anniversary Edition.

Status: **published on Nexus Mods (0.2.7).** The `[v]` and `[x]` markers have been played on the author's setup and show up. See "Known unknowns" for what is still not confirmed everywhere.

## Features

### Known enchantment marker

Enchanted items whose enchantment you have already learned (by disenchanting an item that has it) get a
marker in item lists, so you can tell at a glance while shopping or looting which enchantments you
still need. An enchantment counts as known if you learned it, or if every effect in it is one you have learned
(this includes enchantments you made yourself).

Works in merchant (barter), container, gift and inventory menus. Example: `Iron Sword of Fire [v]`.

Enchanted items the game will not let you disenchant (staves, unique artifacts) get `[x]` instead, so you know
there is nothing to learn from them.

## Requirements

- Skyrim SE / AE 1.6.1170 or 1.7.104, with SKSE and Address Library
- SkyUI (item lists are refreshed through its list)
- MCM Helper, for the settings menu (optional; the files can be edited by hand). The mod ships a small
  `EnchantersHandbook.esp` (light plugin, one quest, no gameplay): MCM Helper only lists a mod whose plugin is
  loaded and has an MCM quest. `tools/make_mcm_plugin.py` regenerates it.

## Settings

In the SkyUI Mod Configuration Menu under "Enchanter's Handbook": on/off, mark your own inventory,
the two markers, and whether they go before or after the name. Without MCM Helper edit:

- defaults, shipped with the mod: `Data\MCM\Config\EnchantersHandbook\settings.ini`
- your overrides: `Data\MCM\Settings\EnchantersHandbook.ini` (wins over the default)

The marker is plain text because Skyrim's fonts lack most symbols. A real graphical icon needs a
modified SkyUI interface file and is a possible future step.

Colored markers and tinted icons are not possible: SkyUI draws item names as plain text and ignores color codes.

## Known unknowns (test these first)

- Whether the marker shows in each menu and the list redraws without flicker or losing your selection.
- Whether items you enchanted yourself count as "known" (they use a player-made enchantment form).
- If the marker never appears, check `Documents\My Games\Skyrim Special Edition\SKSE\EnchantersHandbook.log`.

## Troubleshooting

- **No "Enchanter's Handbook" entry in the MCM:** enable `EnchantersHandbook.esp` in your plugin list (new plugins
  often arrive disabled), make sure MCM Helper is installed, and load a save. Then check
  `Documents\My Games\Skyrim Special Edition\SKSE\MCMHelper.log`: it should list the mod, and a line such as
  `Failed to parse config for EnchantersHandbook` means the config was rejected.
- **No markers on items:** check `Documents\My Games\Skyrim Special Edition\SKSE\EnchantersHandbook.log` for the
  `loading` and `Item menu hooks installed` lines.

## Build

Needs Visual Studio (C++), CMake and vcpkg (`VCPKG_ROOT`, default `C:\dev\vcpkg`).
Run `build_release.bat` from a Visual Studio x64 developer prompt, then `make_archive.bat` for the zip.

## Contributing

**Set up.** Visual Studio with the C++ workload, CMake, vcpkg (`VCPKG_ROOT`, default `C:\devcpkg`) and git.

    git clone --recurse-submodules https://github.com/the3venthoriz0n/EnchantersHandbook.git
    build_release.bat        (from a Visual Studio x64 command prompt)
    make_archive.bat         (writes dist\Enchanters_Handbook_<version>.zip)

There is no automated test suite yet, so the check before a pull request is playing it: install the zip, open a merchant, a container and your inventory, and read `EnchantersHandbook.log` for errors.

**House rules.**
- The packaged DLL must not depend on `spdlog.dll` or `fmt.dll` (they do not exist in a Skyrim install); `make_archive` checks the version marker.
- `package/Data/EnchantersHandbook.esp` is generated by `tools/make_mcm_plugin.py`; change the script and regenerate, do not edit the plugin by hand.
- Do not edit version numbers by hand (see Releasing: the tag is the version).
- Say what you verified in the game and what you did not.
- Commit with your GitHub noreply address, small commits, one concern each.

**Pull requests.** Branch from `main`, open a pull request into `main`, and describe what changed, why, and what you tried in game (paste the relevant log lines). A tag may only be pushed on a commit that is already on `main`.

## Releasing

**To release, tag `main`.** The tag is the version, you never edit version numbers by hand.

1. **Make sure `main` is what you want to ship.** Merge your work, build, install `dist\Enchanters_Handbook_<version>.zip`, play it and read the log.
2. **Pick the next version** (`vMAJOR.MINOR.PATCH`), higher than the version on Nexus.
3. **Tag and push:**

        git checkout main && git pull
        git tag v0.2.8
        git push origin v0.2.8

4. **Watch it:** `gh run watch` (or the Actions tab). The first run on a fresh cache takes a while; later runs reuse the cached vcpkg packages.
5. **Check the result:** the run is green; the GitHub release has `Enchanters_Handbook_<version>.zip`; the Nexus Files tab shows the new version of the existing file; `main` has a new "Bump version to ..." commit from `github-actions[bot]`, so pull it.

**What the workflow does** (`.github/workflows/release.yml`, on a Windows runner): checks the tag looks like `v1.2.3` and its commit is on `main`; stamps the version into `CMakeLists.txt`, `vcpkg.json`, `src/main.cpp` and `tools/make_archive.ps1` (it stops if any of them does not match exactly once); builds; runs `tools/make_archive.ps1`; creates the GitHub release with the zip; uploads the zip to Nexus Mods as a new version of the existing file with a changelog entry pointing at the GitHub release; then commits the bumped version numbers back to `main`.

**Dry run, no release:** Actions tab, "Release", "Run workflow" on `main`: builds and packages, uploads the zip as a build artifact, does not release, upload or commit.

**One-time setup (done for this repo).** Create the Nexus mod page **under Skyrim Special Edition (not "Skyrim", which is the Legacy Edition: files from a Legacy page download into Vortex's `skyrim` folder and Vortex will not install them into a Special Edition game)** and upload the first zip by hand (the action only adds versions to an existing file), then:

    gh secret set NEXUSMODS_API_KEY --repo the3venthoriz0n/EnchantersHandbook          (paste your Nexus API key when asked)
    gh variable set NEXUS_FILE_ID --body <File ID> --repo the3venthoriz0n/EnchantersHandbook
    gh variable set NEXUS_MOD_ID  --body <Unique Mod ID> --repo the3venthoriz0n/EnchantersHandbook

Both numbers are in the file's "Advanced" panel on Nexus: **File ID** and **Unique Mod ID** (the long number, not the number in the page address). Without the secret and `NEXUS_FILE_ID` the Nexus step is skipped and the GitHub release is still made.

**If something goes wrong.** If Vortex downloads the file but never installs it, check that the Nexus page is under Skyrim Special Edition and that the download path in `%APPDATA%\Vortexortex.log` says `skyrimse`, not `skyrim` (pages cannot be moved between games; create a new page, upload the zip and set `NEXUS_FILE_ID` and `NEXUS_MOD_ID` from it). A wrong tag: delete it (`git push origin :refs/tags/vX.Y.Z`, `git tag -d vX.Y.Z`), fix, tag again. If the Nexus step fails after the version was created, the version is already on Nexus: do not re-push the same tag, ship the next patch version. If the bump commit is skipped, make the same four edits by hand or let the next release do it. After a build fix, use the dry run instead of pushing more tags.
